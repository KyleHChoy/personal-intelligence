# @intelligence/claim-pipeline

The parts that turn one evidence item into checked claims: parser, header reader, interaction entry, the interpreter output's check, and the checker. A model proposes; code checks.

- **May import:** `@intelligence/contracts` and three parsers: `postal-mime`, `html-to-text`, `unpdf`. It uses Node's `node:crypto` for SHA-256 only. Anything else must be added to `package.json` deliberately; the import fence test checks the forbidden cases.
- **Runs with:** no credentials, keys or connections of its own. It reaches what it reads and calls only through the arguments and ports it is handed. Personal Intelligence calls the parts below from its own packages, with its own model client.
- **Who uses what:** Personal Intelligence uses `parse`, `segmentAt`, `readHeaders`, `interactionFor`, `check`, `checkOutput`, `verify`, `LIMITS` and `PipelineError`.
- **Never:** reads a store, lets model output set a label, a compartment, a destination, an author or a basis, follows instructions in evidence, logs anything, seals anything, or lets evidence text into an error. Every failure is a `PipelineError` that carries one `FailureCode`.
- **Status:** built for email and for reference documents, with shadow generations, the switch, claims held for identity review and interaction entries, and tested against fakes. What is left is listed at the end.

## What is built

| File | What it does |
| --- | --- |
| `parse.ts` | `parse(item, payload, limits)`: a raw message (`message/rfc822`) through `postal-mime`; an HTML body or document through `html-to-text`; a PDF attachment or document through `unpdf`. An item of a source confirmed as reference is read as a document (see "The document lane"). Any other media type, a message with no sender address, anything over a limit and any parser error end as `parse_failed`. Also `segmentAt(parsed, span)`. |
| `limits.ts` | `Limits`, the type of `PipelineConfig.limits`: what the parser accepts and how much the model is sent. `LIMITS` is the set of values the tests use. |
| `html.ts` | `htmlToText`: a one-pass scan of an HTML part's nesting depth and tag count, then `html-to-text`. `htmlDocumentToText`: the same for a reference document, giving its `<title>` and its text with each heading marked. |
| `sections.ts` | `readSections`: a document's sections and a template's placeholders. `fallbackTitle`. |
| `quotes.ts` | Splits a body so each stretch of text is credited to who wrote it, in one pass. |
| `headers.ts` | `readHeaders(parsed)`: sender, recipients, time, Message-ID and the reply chain, with no model. |
| `interaction.ts` | `interactionFor(parsed, own, deps)`: the header interaction entry of an email. |
| `interpret.ts` | `checkOutput`, which rejects anything that is not exactly an `InterpreterOutput`. |
| `check.ts` | `check(candidates, readSet, context, deps)`: ontology validation, grounding, authorship and basis, identity resolution, the deterministic claim id, the label and every stamp. |
| `read-set.ts` | `verify(item, deps)`, which checks an item's label signature once and makes a `ReadItem`. |
| `hash.ts` | SHA-256 over a value's JSON, and the canonical form of a claim's content. |
| `ports.ts` | `PipelineItem`, and `PipelineDeps`, what `check` is handed. |

## How it works

**Spans.** A span is `chars:<start>-<end>`, end excluded, over the message's plain text body: the `text/plain` part when the message has one, otherwise the `html-to-text` output of its HTML part; for a PDF, the extracted text. Line ends are `\n`. This is the convention of the synthetic organization. Two prefixes name a text that is not the body: `subject:chars:...` and `attachment:<n>:chars:...`. Each parsed segment's span is the range it covers. A claim's span must fall wholly inside one segment of the message being processed.

**Limits.** The limits are configuration: `PipelineConfig.limits` names all eleven. They bound the payload's bytes and line ends, the body's characters, an HTML part's characters, nesting depth and tag count, a line's length, the number of attachments, the bytes of an attachment that is read, the number of segments an item is cut into, and the size of the rendered interpreter prompt. Anything over a limit is `parse_failed`, with no content, no model call and nothing written. `parse` takes the limits as a required argument, with no default. `LIMITS` in `limits.ts` holds the values this package's own tests run under; no app falls back to them. The splitter is one pass over the body's lines with no pattern that can backtrack, and quotes nested deeper than eight are read as text.

**HTML.** The parser under `html-to-text` does work that grows with the square of the nesting depth, and `html-to-text`'s own limits apply only after that parser has run. So `html.ts` reads the HTML once first. `htmlTags` counts every `<` followed by a letter, wherever it stands: no parser can open more elements than that, so the bound holds whatever else the scan gets wrong. `htmlDepth` is the deepest the open elements get, followed the way the parser follows them: void elements, the closes an opening tag implies, quoted attribute values, comments, and the text inside `script`, `style`, `title`, `textarea` and `xmp`. Over either bound the item is refused before any conversion.

**Crediting.** A parsed segment has an author, or none when the author cannot be told. Nothing is ever credited to a guess.

- The sender's own text is the sender's.
- A run of `>` lines is a quote. White space of any kind, and zero-width characters, may stand before a marker. Blank lines alone do not end it. Its author comes from the line that introduces it: a line ending in a colon, right above the quote or as its first line, possibly wrapped in two. That line must give an address, or the whole display name, on word boundaries, of someone in the message's own From, To or Cc. No name is looked for in a line longer than 300 characters, and a display name two addresses share names nobody. A quote nothing introduces has no author, and takes nothing from the quote before it.
- A forwarded or original message is a run of `Name: value` lines, with at most one blank line between two of them, that holds a From line and at least two of Sent, Date, To and Subject, in any order. The names are matched as mail clients spell them in English, German, French, Spanish, Portuguese, Italian and Dutch. A signature, an agenda or a contact card is not one, and leaves the sender's text the sender's. The block's author is the address or whole display name on its From line, otherwise nobody. The line right above the block is dropped only when it is a delimiter (it begins and ends in dashes or underscores) or reads "Begin forwarded message:"; any other line stays. The text after the block is its author's to the end of its first paragraph. Past that, nothing marks where the forwarded text stops, so the rest has no author, until the quote the block sits in ends. A block at the top level never gives the text back to the sender.
- The text of a PDF attachment, and of an HTML or PDF document, has no author.

**Automated senders.** Flagged from the sender's mailbox name (the no-reply forms, RFC 2142 names and common shared inboxes) and from the `Precedence`, `List-Id`, `List-Unsubscribe` and `Auto-Submitted` headers. An automated sender is never credited as a person.

**The reply chain.** The chain is read from the message's own `In-Reply-To` and `References` headers, nearest first, each id once, cut at `PipelineConfig.replyChainDepth`. `processItem` looks each Message-ID up in the same source account through `EvidenceReader.byMessageId`. A reply the vault does not hold there, whose payload is gone or in quarantine, or that cannot be parsed, is skipped and is not in the read set. A reply whose label does not verify fails the item. The claim's label, its keys and the saved interpreter call cover exactly the items read.

**The checker.** A model may only narrow. `checkOutput` parses the output as `InterpreterOutput`. The contracts' schemas are strict, and refuse a label, reader, compartment, destination, store, grant or clearance key in any letter case, singular or plural, at any depth of a claim's fields; any failure rejects the whole output (`interpret_failed`). Then, for each candidate, in this order:

1. The type must be an ontology type with an owner (`unknown_type`), and its fields exactly the type's fields, each of its declared kind (`bad_fields`). A date is a contracts `Timestamp` or `DateOnly`. A type field is an ontology type id, or a phrase the ontology resolves to exactly one.
2. The span must fall inside one segment of the message (`bad_span`).
3. When the candidate gives both `validFrom` and `validTo`, the end must not be before the start (`bad_times`). A claim must carry a `validFrom`, so with none given it is the item's time, or the candidate's `validTo` when that is earlier: a statement about the past is kept, with its start no later than its end.
4. Every address the candidate names, as subject, context or entity field, must appear in the item's headers or text; a source id never does (`ungrounded_mention`). A mention keeps only its key: its time is the item's, never the model's.
5. The cited segment must have an author (`author_unknown`). The one exception is an enforced policy of the document lane: a document's text has no author, so its claim is credited to nobody.

A candidate that fails a step is stored unmapped with that reason code, under its type's id or `other`, and is not routed. Otherwise:

- The store is the type's owner. The subject, the context mention and every entity field are resolved through `IdentityResolver`, once for each mention and item. `linked` and `created` give an entity; `candidate` holds the claim back and reports the review id; `not_a_person` and `suppressed` give nothing. A name-only mention never creates an entity. A failed call fails the item (`control_unavailable`). The request id is a hash of the evidence id, the revision, the extractor generation, the interpreter call's input hash, the candidate's position in the output and which mention it is (`subject`, `context`, `field:<n>`, `speaker`). It never depends on the mention's value, and an extraction that was shown anything different never repeats another one's ids. With each of these mentions the resolver is told where it came from (`from`): the passage the claim cites, the vault, and the label the claim carries, which is the combined label of everything the extraction read, narrowed.
- `assertedBy` is worked out in code. For the sender's own words it is the sender. For a quote it is the quote's author only when the quoted text, white space aside, is whole lines or whole sentences of the own words of a message that author sent and that was read in the reply chain: it must start where a line or sentence starts and end where one ends. A fragment, such as a sentence with its "not" cut off, and any other quote, is a report by the sender who passed it on. An automated sender is nobody. The candidate's own `assertedBy` is not used.
- `basis` is worked out in code and never copied: `explicit_self` when the cited text is unquoted and its author is the claim's subject, `third_party` otherwise. A quote is never `explicit_self`, and `system_observed` and `web_derived` never come from the interpreter.
- The label is the combined label of the read set, then narrowed in code through `narrow` (`labels.ts`). `special_category` adds `PipelineConfig.specialCategoryCompartment`, the only addition allowed. `participants_only` keeps only the members on the message itself: the ones ingest recorded on the item when it wrote it (`EvidenceItem.participantMembers`). The library asks no directory and takes no port for them. With no record of them, nobody is kept, so the claim is visible to nobody without a grant. `quarantine` yields no claim and `processItem` moves the item to quarantine.
- The id is SHA-256 over evidence id, revision, span, canonical content and extractor generation. The content is the candidate's type, subject key, checked fields, statement kind, context, `validFrom` and `validTo`, and the basis code worked out, taken before identity resolution, with keys sorted. A mention, in a field as elsewhere, counts by its key alone, so the time a model put on it changes nothing.

**Claims held for identity review.** A claim whose subject, context or entity field is only a candidate is not routed and is not stored unmapped. The batch names the reviews the item's claims wait on (`CommitBatch.held`), so the writer can keep them and the app can run the item again; an item whose only content is a held claim is still committed. A run made again carries `PipelineDeps.rerun`, a number that names the run and is never used twice for an item (the app passes the time of the run). On such a run a mention that still answers `candidate` is asked about once more, under a request id that adds the review id and that number to the first one. The identity service keeps the first answer of a request id, so without the new id it would answer `candidate` for ever; with it, it answers by the review's decision once there is one, and with the same review until then. The claim's id does not depend on identity resolution, so the claim released is the one that was held. A run made again always says what is still held, an empty list included, so a settled review is let go. A shadow run holds nothing.

**Interaction entries.** `interactionFor` makes an email's `InteractionRecord` from its headers, with no model: who sent it, who it went to and when. The time is the `Date` header only when that is not after the time the connector saw the item (`observedAt`); a header that claims a later time is the sender's word and is not used, and the entry takes `observedAt`. The parser reads the header by one fixed grammar, the date RFC 5322 writes with a four-digit year, and gives it as a `Timestamp` in UTC or not at all: a date with no zone is UTC, and one that is not such a date, that names a zone with no known offset, or that a `Timestamp` cannot hold (a year below 100 or above 9999) is read as absent, so the entry takes `observedAt` then too. `interactionFor` checks the time against `Timestamp` before using it, because the store refuses a record whose time is not one. Every address is resolved through `IdentityResolver` for the People store, under a request id that says where the address stood in the headers; one that is no person, is suppressed or is only a candidate is left out of `participants`. The members are the ones ingest recorded on the item. With `senderMember` the item was sent by a member: the entry is outbound, names that member as `sender` and carries `sent`, the recipients and `messageBodyHash` of the message's own plain text body. Without it the entry is inbound and `participantMembers` are `teamRecipients`. An item with no `participantMembers`, an automated sender and an item with no sender leave no entry. The entry reads its own item only, so its message carries that item's label and key, not the reply chain's, and it goes to People in the same batch as the item's claims. A quarantined item leaves none.

**What is left to trust the model for.** The type, the fields, the subject and the span. A model can still cite a span whose text does not say what the claim says; a check that compares a quoted string with the span's text is not built.

`parse` also returns `texts`, the strings its segments' offsets index (the body under `""`, the subject under `subject:`, each read attachment under `attachment:<n>:`), so another process holding the same bytes, the provider cutting a cited span, slices exactly what the pipeline counted.

## Not built yet

- Parsing for items other than mail and reference documents. Personal Intelligence builds its calendar events, chats, meetings, contacts and captures with its own item builders (`src/items`), which do not pass through `parse`. A `workbench_correction` item is refused before any read.
- Header claim candidates: the header reader makes interaction entries and no claims.
- A reference document's exported file (`DocumentContent.file`) and a section's `guidance`. Nothing in a document's content marks either.
- A check of a claim's whole content against the text of its span. The checks Personal Intelligence runs on how each field stands in its passage are in `packages/extract`.
- Signatures as structured fields, attachments other than PDF, and claims from attachment text, which has no author.
