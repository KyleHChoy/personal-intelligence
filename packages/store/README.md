# @intelligence/personal-store

The only code that touches the personal database. It creates roles and applies migrations, holds the key file, seals and opens content, writes each source item with what the shared header reading and the personal item facts found in it, resolves addresses for them, and runs the read tools' fixed queries under a client's token.

- **May import:** `@intelligence/contracts`, `@intelligence/personal-core`, `@intelligence/personal-beliefs` (the computed belief, its shadow and its measure). It also uses `pg`.
- **Runs with:** one database role per object, chosen by its caller (`Writer` with `pi_writer`, `Reader` with `pi_reader`, `Admin` with `pi_admin`, `Pipeline` with `pi_pipeline`, `ensureRoles` and `applyMigrations` with the bootstrap role), and the key file. Every object takes a `PersonalLogger`.
- **Must never:** build SQL from client input, return a row the database did not return under the caller's token, compute a count or ranking over rows the caller cannot see, write plaintext content, log anything but ids, counts and codes, write to stdout.
- **Entry points:** `@intelligence/personal-store`, a subpath entry per bounded context (below), `./keys`, and `@intelligence/personal-store/testing` for database tests.
- **Status:** built:
  - the database (roles, migrations, keys), the `Writer`, the `Reader` and the `Admin`;
  - every message stored with its text, which the two message tools read;
  - extraction's tables, the `Pipeline` that serves them, and the reader's `find_facts`;
  - agent records: appended, taken into the vault, and removed with what they rest on;
  - context packs, for a client registered with `build_context_pack`;
  - the screening model's state: the recovery mark and its backlog (`Pipeline.markRecovery`), the run's thresholds, an item withheld as an injection (kept across revisions and re-derives), and the saved pair calls (`vault.decision_calls`), removed with what they rest on;
  - `admin.calibration` (verdicts, reviews, reports, proposals, grants, targets, suspensions, the drift card, the release of a flagged finding);
  - the identity ranking's prompt and order (`identity-points.ts`), which the identity sweep uses within each tier.

## Bounded contexts

A context may import only the contexts its row in the store-contexts structure test names, all of them earlier in this list, so the table has no cycle; `core` imports none. The imports that run against the order today are named in that test's `CROSSINGS`, which may only shrink: the shared modules that depend only on `core` (`item-origin.ts`, `capture-pages.ts`, `activity-keys.ts`, `link-types.ts`, `claim-order.ts`, `night-store.ts`, `read-tool.ts`, `promotion-revoke.ts`) have moved down into it, and most that remain are modules other features call into a feature folder. Each context that other packages use has a subpath entry, `@intelligence/personal-store/<context>`, whose `index.ts` exports what they import from it today; the package root re-exports the same names.

## Connections

Every connection takes its URL through `parseDatabaseUrl` (`src/core/db.ts`), which refuses one that does not parse with `bad_url` and nothing of it, and sets TLS (`withTls`): a URL to a host other than `localhost`, `127.0.0.1`, `[::1]` or a socket that names no `sslmode` gets `verify-full` when it names a CA in `sslrootcert`, as the box's entrypoint makes every role's URL once the owner has put the CA on the volume, and `sslmode=require` when it names none, which the coverage record raises as a `tls_unverified` box health card; each with libpq's meaning of each (`uselibpqcompat=true`). A local URL, the local Docker server's included, is left as it is, and a URL that names its own `sslmode` keeps it: `sslmode=disable` is the switch for a test server on another host that has no TLS.

## Refusals

`KeyFileRefused` (`exists`, `mode`, `check`, `format`, `missing`, `locked`, `changed`, `wrapped`, `restricted_key_file_unset`) and `MigrationRefused` (`changed`, `missing`, `bad_name`, `transaction_control`) are classes. Every other refusal is a plain `Error` with a string `code`: `unknown_compartment`, `account_mismatch`, `invalid_address`, `invalid_argument`, `invalid_item`, `invalid_facts`, `role_attributes`, `not_owner`, `needs_superuser` (the unattended migration, for a file the migration role cannot apply), `bad_url`. `AdminError` (`invalid_registration`, `duplicate_name`, `invalid_address`, `not_found`, `invalid_argument`, `confirm_needed`, with the count selected, `extract_running`, `unknown_compartment`, `record_disabled`, `too_many_compartments`, for a clearance of more than 32 compartments, and the promotion gate's `not_promotable`, `invalid_promotion` and `promotion_revoked`) is a class too. A database error reaches the writer's caller as `unavailable`, or as `write_refused` when the database refused a value or a constraint, which no retry mends. Its `cause` is `{ sqlstate, constraint }` and nothing else of the driver's error, whose message can quote a value. A stored value the writer cannot open, whether its key is wrong or absent, throws an error named `CryptoError` with code `open_failed`; with no key for its compartment it is never opened at all, and with a restricted key that is wrapped and not unlocked it is refused with `restricted_locked`.

## Messages

The store holds a message's text twice, sealed both times: in the vault, inside the message's evidence blob, and in `knowledge.messages.body_enc`, the copy the message tools read, so the reader needs no grant on `vault`. Each envelope is bound to its own row and column, so neither opens as the other. An attachment's bytes are never stored: only its name, type and size, sealed with the message's other facts. Every stored email that was read has one row in `knowledge.messages`, bulk mail included; a bulk message has that row and nothing else.

A held message, one that matches the recovery markers, has its row like any other and is served to no client until the owner releases it: the reader's row policy on `knowledge.messages` leaves out every row with `held` true, whatever the statement. The release is a time on the message's evidence row. A later revision copies it and a re-derive reads it, so a released message is never held again.

## Documents

Google Drive and Docs.

- One row in `knowledge.documents` for each stored document, citing its latest revision and updated in place, so its id stays; the re-derive neither derives a document again nor touches its row. The vault keeps one original for each document: when the next revision is stored, the earlier revision's blob is deleted and its evidence row keeps its record and hash, marked `expired`. A message's revisions keep their blobs.
- A document whose `root:` marker names no root of its label is not stored (`left`). What left the owner's scope (`finishPage`'s `leftIds`, a complete listing that did not name it, a root the owner removed) is removed through `removeSourceItem`, as a deletion is, with no removed-evidence row, so it is stored again when it returns. Only the owner's `eraseItem` sticks against the source; `hasRevision` answers true for an erased item, so the connector does not fetch it again.
- A document is held when its title or first 2 000 code points match the recovery markers. The reader's policy hides a held row; the owner releases one with `releaseHeldDocuments`, and a new revision that still matches is held again. Nothing of a document makes an entity, an alias or an interaction row; an owner or sharer whose address is suppressed is stored with no fingerprint or sealed value for them, and erasing a person clears them from documents through the `documents` erasure hook.
- `policy.drive_roots` holds the roots: a folder id or the words `my-drive` and `shared-with-me`, sealed under `own`, matched by a keyed fingerprint. `pi_admin` writes them, `pi_writer` reads them, and neither the reader nor the pipeline can read one. Setting a root's mode and removing a root take the sync lock first.
- The reader's `findDocuments` filters on clear columns and fingerprints, and opens at most 5 000 titles for a title search; `getDocument` returns a window counted in UTF-16 code units, at most 50 000, with the result kept under 60 000 code units as JSON.

## Extraction

Their labels are held by triggers: a claim is labelled as its evidence and a claim entity as its claim. No belief is stored: every answer is computed at read under the caller's clearance, labelled by the union of its support's labels. Every path that removes an item takes its locks in one order: the message row, then the evidence rows `for update`, then the beliefs lock, and removes what was extracted from it in the same transaction. A re-derive removes every claim and sets each status row's generation to 0, keeping the owner's lane and release. `pi_pipeline` reads the evidence, may lock an evidence row and change none, and reads only `openrouter/*` secrets; `pi_writer` reads only `google/*` secrets.

The tool names are rows of a table, `policy.tool_names`, which `policy.calls.tool` references. A later migration adds a tool with one plain `insert`; no runtime role can add, change or remove a name.

## Settled facts: one owner's answer per fact

`fact-settlements.ts`. An agent record's claim carries its match key (`ClaimRecord.matchKey`, set by the pipeline from the content); the commit stores its fingerprint on the card it raises (`ledger.cards.match_fp`, set once). Before raising, it asks `policy.fact_answer` (definer, `pi_pipeline` alone) within the label guard: an open card on the key, then the owner's latest answer that `decide` wrote. A claim it answers raises no card and writes a `ledger.fact_settlements` row. `decide` turns the claims waiting on a card into the owner's answer and withdraws the other undecided cards on its key, but those named in the call, adding them to its one lock call. Once each run, `raiseSettledClaims` raises the card of a reopened settlement and of the first claim waiting on a card that ended without the owner's answer. Settlements are append-only but for `reopened_at`; the latest row of a claim key is in force. The pipeline reads only its own rows.

## Identity merges by policy

The sweep (`identity-sweep.ts`) computes each pair's exception (`groups.ts`'s `exceptionOf`, the one place they are written) from its read, with established people and namesakes counted only within the pair's labels. A pair no exception holds goes to `ledger.policy_merge` (definer, `pi_writer` and `pi_admin`), in a transaction whose one lock call is the function's; a refusal rolls it back and the pair is carded as before. The cap of ten open cards stops only carding. The writer stores each account's `local_name_fps` when it writes one; `backfillLocalNames` fills older rows. `dryRunIdentity` reads what a sweep would do and writes nothing.

## Using the writer

Writer calls for one database must not overlap, except through `withSyncLock`: two items that share a new address, ingested at once, would each make an entity for it. `pi sync` ingests in order under the lock. A sync whose lock connection is lost writes nothing more: every writing call rejects `unavailable` until its `withSyncLock` ends.

## The reader and the admin

Both take a pool (`new Reader({ pool, keys, log, now? })`, for a test that wraps one) or make their own (`createReader`, `createAdmin`), and use only `pool.connect()`, `client.query(text, values)` and `client.release()`. `close()` ends only a pool the factory made. `createAdmin({ timeoutMs })` gives its pool a connect, statement and query timeout, for `pi models import-key`.

The reader never names a compartment: row-level security returns only the rows the token is cleared for, and every count, rank and order is over those rows. A call opens values with the keys of its client's compartments alone, so a row of another compartment that reached the reader would not open, and the call would answer `unavailable`. No token, an unknown token and a revoked token take one path of four statements and answer `unauthorized`. The token is set only when `session_user` and `current_user` are both `pi_reader` and `row_security_active('policy.clients')` is true, so a reader given any other role's URL, a superuser's or one that bypasses row-level security included, refuses every call: `unauthorized` where that role can run the `current_client()` lookup, and `unavailable` where it cannot, as `pi_admin`, `pi_writer` and the bootstrap cannot. Every statement that names `knowledge` ends in an `order by` that includes a unique key. Every call that ends `ok` writes its read set to `ledger.read_log` under the client's session, through the definer functions `policy.open_session` and `policy.log_read`: the reader still holds no insert, update or delete privilege on any table. A refusal is an outcome, never a throw: `unauthorized`, `not_permitted`, `invalid_request`, `not_found`, and `unavailable` for a database error or a value that does not open, logged as `read_failed`. `client(token)` throws a plain `Error` with code `unavailable` for the same failure, since it has no outcome to return.

The admin throws `AdminError` (`invalid_registration`, `duplicate_name`, `invalid_address`), and a database error as a plain `Error` with code `unavailable`, logged as `admin_failed`. Its `cause` is `{ sqlstate, constraint }` and nothing else of the driver's error, as the writer's is. The reader's errors carry no cause at all.

## Tests
